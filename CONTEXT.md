# Portfolio Website Context

> **Handoff brief for a coding agent.** Build the walking skeleton defined under [Skeleton scope](#skeleton-scope). That means every box in the repository layout exists and is wired end to end, with minimal implementation and placeholder content. Anything listed under [Out of scope](#out-of-scope) is not part of this task. Where this brief is silent, use the defaults under [Open decisions](#open-decisions) and say in the PR which ones you relied on.

### Objective:
Create a portfolio website with Astro 6, hosted on Cloudflare Workers, that updates nightly. A scheduled **GitHub Actions** workflow does the update: it pulls repository data from the GitHub GraphQL API, rebuilds the site, regenerates the résumé PDFs and deploys. The **Cloudflare Worker** only serves the prebuilt static files. It runs no code and does no updating.

The site's job is to put every claim one click from its evidence: skills link to projects, and projects link to repos, demos and case studies.

The owner is a test architect. Treat the test suite and CI as part of the portfolio: they are first-class deliverables, not afterthoughts.

### System Considerations:
- This setup should take relevant content nightly and publish it to the hosting service for external viewers to see.
  - The nightly job is a GitHub Actions `schedule` workflow. It fetches GitHub data, rebuilds and deploys. Nothing changes between builds. A content change merged to `main` triggers the same build and deploy.
- There will be three different project tracks to consider:
  - Non-profit work
  - Day to day role
  - Technical side projects
- When a visitor lands on the site they can choose which track to follow.
  - The track titles match the categories above exactly (see [Tracks](#tracks)).
  - The track selector is plain links, with no client-side JavaScript.
- Each page in `src/pages` is an `.astro` file that Astro compiles to static HTML at build time. The Worker serves the files in `dist/`. Nothing renders at request time.
  - `for/[track].astro` is a single dynamic route file. Its `getStaticPaths()` emits one page per entry in `tracks.yaml`, so each category gets its own URL: `/for/nonprofit/`, `/for/professional/`, `/for/side-projects/`.
- The `projects/[slug].astro` pages use each MDX file's name as the slug.
  - For projects that live in one of the owner's GitHub repositories, the filename must equal the repository name, lowercased. An integrity test enforces this.
  - Projects with no public repository (most day-to-day-role and non-profit work) still get a page. They simply have no `repo` field.
- The content folder holds the files that describe the projects completed, experience gained, skills built, milestones reached, and the tracks that organize the site. Projects are MDX (frontmatter plus a case-study body). Everything else is YAML. All of it is validated against the schemas below.
  - These files generate the résumé PDFs, one per track.
  - The site updates from the same files, so the site and the PDFs can never disagree.

## Content schemas

Field rules live as plain Zod objects in `src/lib/schemas.ts`, so they can be unit-tested without Astro. `content.config.ts` imports them and adds loaders and `reference()` fields.

Dates are `"YYYY-MM"` strings, checked with a regex. `src/lib/dates.ts` converts them for sorting and display ("Mar 2026").

Image fields are the exception to keeping every rule in `lib/schemas.ts`, because the `image()` helper only exists inside a collection's `schema: ({ image }) => …` function. In `lib/schemas.ts`, declare image fields as relative-path strings so the unit tests can run. In `content.config.ts`, extend the schema to replace them with `image()`, which makes Astro check at build time that each file exists.

## Integrity rules

Implement these as pure functions in `src/lib/integrity.ts`. They take plain objects (parsed frontmatter and YAML), not Astro runtime data. Two things run them:

- `scripts/check-content.ts` reads the raw files and runs every rule. It fails the build on any violation and runs before `astro build`.
- Vitest runs every rule against valid fixtures and against **at least one invalid fixture per rule** in `tests/fixtures/invalid/`. Each invalid fixture must fail its rule.

1. Every reference resolves to an existing entry.
2. Exactly one track has `default: true`.
3. Every track has at least 1 non-draft project. Raise this to 3 before the custom domain is attached.
4. A repo-backed project's id equals its repository name, lowercased.
5. `confidential: true` means no `repo` and no `demo`.
6. Every skill's evidence points only to non-draft projects.
7. **Strict content mode:** when `STRICT_CONTENT=true`, no content file may contain `TODO(owner)`. It's off for the skeleton. The owner turns it on before attaching the custom domain.
8. Every image has alt text: a set `cover` needs a non-empty `coverAlt`, and every `gallery` item needs a non-empty `alt`.
9. Every image a project references lives in `src/assets/projects/<that project's id>/`.
10. No image file under `src/assets/` or `public/` contains GPS metadata. Check with `exifr`.
11. No image file is larger than 5 MB (a constant in `integrity.ts`), and there are no video files (`.mp4`, `.mov`, `.webm`, `.mkv`) anywhere under `src/` or `public/`.

Ranking lives in `src/lib/rank.ts`: `rank(projects, trackId)` returns the track's non-draft projects with featured ones first, then ongoing projects, then by most recent `period.end`, falling back to `start`. Unit-test it.

## GitHub data (`scripts/fetch-github.ts`)

- **Input:** the `repo` field of every non-draft project. Parse the frontmatter directly with a YAML/frontmatter parser rather than importing Astro.
- **Request:** one GraphQL query that uses one alias per repository. For each repo fetch `nameWithOwner`, `description`, `url`, `homepageUrl`, `primaryLanguage { name }`, the top 5 `languages` by size, `stargazerCount`, `pushedAt`, `isArchived`, and the default branch's latest commit `committedDate` and `statusCheckRollup { state }`. Map a null rollup to `"none"`.
- **Auth:** the `GH_GRAPHQL_TOKEN` environment variable.
- **Output:** `src/data/github.json`, shaped as `{ fetchedAt, source: "live" | "cache" | "fixture", repos: { "<owner/name>": {...} } }`, with sorted keys so output is deterministic. The site reads it through a `file()` collection with its own schema.
- **Failure policy: fail on wrong data, tolerate missing data.**
  - No token (a fresh clone, or a PR from a fork): copy `tests/fixtures/github.json`, set `source: "fixture"`, print a warning, exit 0.
  - A listed repo comes back `NOT_FOUND`: exit 1. That would be a broken link on the site.
  - Network error, HTTP 5xx or a rate limit: keep the existing `github.json` (CI restores it from the Actions cache) with `source: "cache"`. If there is none, use the fixture. Print a warning and exit 0.
- The colophon page shows `fetchedAt` and `source`.

## Images

**Where image files go**

| Location | Use for | Processing |
|---|---|---|
| `src/assets/projects/<slug>/` | Screenshots, photos and diagrams for one project | Optimized at build time: resized, converted to WebP, given `width`/`height`, lazy-loaded |
| `src/assets/site/` | Site-wide images (a portrait, if the owner adds one) | Same as above |
| `public/` | The favicon, `robots.txt`, and any file that must keep an exact URL | None: served exactly as stored |

Project MDX files stay flat (`projects/<slug>.mdx`). Don't move them into folders per project. That would change how Astro generates entry ids and break the slug-equals-repository-name rule.

**How content uses images**
- **Frontmatter:** `cover` and `gallery` (see the projects schema). Pages render them with `<Image />` or `<Picture />` from `astro:assets`.
- **MDX body:** a Markdown image with a relative path into `src/assets/projects/<slug>/` is optimized automatically. Import `<Image />` or `<Picture />` into the MDX file when a figure needs set sizes or formats.
- **Diagrams:** prefer SVG exports (Excalidraw, draw.io, Mermaid). They stay sharp at any size and are small.

**Rendering rules**
- Never use a raw `<img>` tag for a file in `src/assets/`. Always go through `astro:assets`.
- Any image wider than the text column sets `widths` and `sizes`, so phones don't download desktop-size files.
- An image visible on first load (above the fold) uses `loading="eager"`. Everything else keeps the lazy-loading default.
- **Résumé pages contain no images.** The PDFs must stay plain text so applicant tracking systems can read them.

**Video:** never commit video files (integrity rule 11). Demo recordings get hosted elsewhere, unlisted, and linked. Embedding video is out of scope for the skeleton.

## Résumé PDFs (`scripts/render-pdfs.ts`)

After `astro build`, the script:
1. Starts `astro preview` on a local port.
2. For each track, has Chromium (via Playwright) open `/resume/<slug>/` and call `page.pdf()` with `preferCSSPageSize: true` and `printBackground: true`, writing the file to `dist/resume/<slug>.pdf`.
3. Stops the preview server.

It has to run before deploy so the PDFs ship inside `dist/`.

## CI workflows

| File | Triggers | Steps |
|---|---|---|
| `pr.yml` | `pull_request` to `main` | Set up Node from `.nvmrc` → `npm ci` → restore the `github.json` cache → `npx playwright install --with-deps chromium` → `check` → `test:unit` → `build` → `pdf` → `test:e2e`. Needs no secrets: it uses the fixture fallback. **No deploy.** |
| `main.yml` | `push` to `main`, `workflow_dispatch`, `workflow_call` | The same steps as `pr.yml` with `GH_GRAPHQL_TOKEN` set, then `npx wrangler deploy` (with `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`), then the `@smoke` tests against `vars.SITE_URL`, then saving `github.json` to the cache after a live fetch. |
| `nightly.yml` | `schedule: '17 8 * * *'` (08:17 UTC) and `workflow_dispatch` | Calls `main.yml` through `workflow_call`, so the build steps exist in one place only. |

- Every deploy job uses `concurrency: { group: production-deploy, cancel-in-progress: false }` so a push and the nightly run never deploy at the same time.
- The cron minute is deliberately off the hour. GitHub delays scheduled runs at busy times, and the start of every hour is busy.
- GitHub turns off scheduled workflows in public repos after 60 days without repository activity. Note this in the README. The colophon's "data refreshed" date is how anyone visiting the site would notice.
- An optional composite action at `.github/actions/setup/action.yml` can hold the shared setup steps.

## Guardrails (the agent must follow these)

- **No invented content.** Anything unknown is a `TODO(owner)` placeholder.
- **No domain or DNS changes.** Don't add `routes`, don't attach custom domains, and don't touch DNS records.
- **No runtime code.** No Worker script (`main`), no `@astrojs/cloudflare` adapter, no SSR and no live collections.
- **No client-side framework.** Ship zero JavaScript unless a feature in this brief requires it (none does).
- **No secrets in the repo.** Add `.env`, `.dev.vars` and `src/data/github.json` to `.gitignore`. Deploys run only from `main.yml`.
- **Confidential work stays generic.** Day-to-day-role projects describe approach and outcomes, never proprietary systems, code or data.
- **No coursework code.** Nothing from MS course assignments goes into public repos or onto the site.
- **No homelab exposure.** Never link to or embed services running on the owner's home network.
- **No location metadata in images.** The repo is public, so an original photo in `src/assets/` exposes its GPS data to anyone who clones it, even though the optimized output strips it. Integrity rule 10 enforces this. The README tells the owner how to strip it, for example `exiftool -gps:all= <file>`.
- **People in photos need consent.** Don't add photos with identifiable people unless the owner confirms they agreed, and never add identifiable minors.
- **Day-job screenshots follow the confidentiality rule.** No internal dashboards, hostnames, data or tooling.
- **Pin versions.** Use exact versions in `package.json`, commit the lockfile, and pin `compatibility_date`.

## Owner setup (manual, not for the agent)

1. Create the GitHub repository. It's public so the code and CI double as portfolio pieces.
2. Create a Cloudflare API token from the "Edit Cloudflare Workers" template and save it as the repo secret `CLOUDFLARE_API_TOKEN`. Save the account ID as `CLOUDFLARE_ACCOUNT_ID`.
3. Create a fine-grained GitHub personal access token with read-only access to public repositories and save it as `GH_GRAPHQL_TOKEN`.
4. After the first deploy, set the repo variable `SITE_URL` to the workers.dev URL.
5. **Later, not part of the skeleton:** replace every `TODO(owner)`, set `STRICT_CONTENT=true` in CI, raise integrity rule 3 to 3 projects per track, then attach the custom domain. Cloudflare can't create a Workers Custom Domain on a hostname that already has a CNAME record, and it creates its own DNS record for the domain, so remove any existing A or CNAME record on the apex first.
